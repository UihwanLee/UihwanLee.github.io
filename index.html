02

길드 레이드 시스템

6주 · 181 커밋 · 66 파일

길드원이 함께 보스에 도전하고 누적 데미지로 순위를 겨루는 콘텐츠입니다. 서버 API 설계부터 보스 구현, UI, 라이브 반영까지 전 구간을 담당했습니다.

구현 범위

  • 서버 API 7종 설계 및 도메인 모델링
  • 보스 3패턴 구현 — 패턴별 타겟팅 · 범위 판정 · 연출
  • 누적 데미지 랭킹 (길드별 / 멤버별), 실시간 HUD
  • 강화 스택 시스템, 길드 퀘스트, 보상 수령, 레드닷
  • 일일 UTC 리셋 및 시즌 모듈

확장을 고려한 구조 설계

기존 보스 시스템을 재사용하면서, 레이드 고유 특성(불사 · 백그라운드 배치 · 패턴 스케줄)만 추상 베이스 클래스로 공통화했습니다. 보스별 튜닝값은 오버라이드 가능한 속성으로 열어두어, 다음 보스를 추가할 때 패턴 3개만 구현하면 되도록 만들었습니다.

Troubleshooting 01

누적 데미지 정합성 — 랭킹 점수의 신뢰 문제

문제
누적 데미지가 곧 랭킹 점수인 콘텐츠에서 집계가 어긋나는 경우를 발견했습니다. 보스 패턴이 사라진 뒤에도 충돌체가 남아 같은 공격이 중복 집계되고 있었고, 유닛의 랜덤 타겟 탐색이 패턴이 아닌 보스 본체까지 조준하는 문제도 함께 있었습니다.
위험도
길드원끼리 경쟁하는 콘텐츠라 집계가 어긋나면 순위가 실제 기여와 달라집니다. 중복이 항상 발생하지 않아 재현 조건을 잡기도 어려웠습니다.
해결
충돌체 생명주기를 패턴 소멸 시점에 맞춰 정리하고, 패턴이 활성인 구간에만 조준 대상이 되도록 별도 플래그로 분리했습니다. 또한 패턴이 자체적으로 점수를 쌓지 않고 본체로만 위임하도록 해 집계 경로를 하나로 모았습니다.
배운 것 — 버그의 크기는 코드가 아니라 유저가 받는 영향으로 판단해야 합니다. 점수가 걸린 시스템에서 집계 소스가 여러 곳이면, 어긋났을 때 추적조차 어렵습니다.
Troubleshooting 02

기존 시스템과의 충돌 조정 — 라이브 서비스의 제약

문제
제가 만든 보스 공격이 다른 담당자가 관리하던 칩 · 모듈의 면역 효과와 충돌했습니다. 어떤 면역은 막아야 하고 어떤 면역은 막으면 안 되는데, 혼자 정할 수 없는 문제였습니다.
해결
각 시스템 담당자와 기획 의도를 확인하며 면역 종류별 적용 여부를 하나씩 정리했습니다. 반사 보호막은 관통, 방주 모듈·위급 면역은 존중하는 것으로 정책을 확정하고, 이후 보스가 추가돼도 같은 기준을 쓰도록 패턴이 본체 정책을 상속하게 구조화했습니다.
배운 것 — 새 기능을 만드는 것만큼 기존 기능을 깨뜨리지 않는 것이 중요했고, 그러려면 결국 다른 담당자와 이야기하는 수밖에 없었습니다.

그 외 해결한 문제

  • 패턴 주기 드리프트 — 모션 소요시간이 주기에 누적되어 HUD 타이머와 어긋나던 문제를, 절대 경과 시간 기준으로 재계산해 해결
  • 조용히 멈추던 패턴 루프 — 취소 외 예외가 삼켜져 로그 없이 루프가 죽던 문제를 예외 로깅으로 노출
  • GC 부담 — 초당 수백 회 발행되는 이벤트 객체를 단일 인스턴스 재사용으로 전환
  • 회전·플립 패턴의 타격 판정 — 스프라이트와 판정 박스가 어긋나던 문제를 매 프레임 좌표 변환으로 정합
03

컨베이어 벨트를 따라 보상이 흐르고, 액션 자리에 도달한 슬롯을 무료 또는 결제로 수령하는 이벤트입니다. 기획 해석부터 UI · 데이터 · 결제 연동까지 혼자 담당한 첫 콘텐츠입니다.

설계와 개선

  • 슬롯을 생성·파괴하지 않고 7개를 재활용하며 위치만 순환
  • 1차 설계에서 상·하단 컨테이너를 2개씩 교대 운용(16슬롯) → 8슬롯 운용으로 재설계해 동일한 시각 효과로 리소스 절감
  • 슬롯 간 슬라이드 거리 자동 계산, 리바인드 시 렌더 순서 갱신으로 레이아웃 정합성 확보
  • 레벨 구간별 보상 시퀀스 + 구간 소진 시 무한 루프 사이클
  • IAP 결제 연동 — 슬롯 단위 상품 등록
Troubleshooting 03

상태 이중화 제거 — 버그 3건의 공통 원인

문제
레벨업으로 보상 시퀀스가 교체될 때 버그가 연달아 발생했습니다. UI를 닫았다 열면 데이터가 유실되고, 이전 시퀀스와 새 시퀀스가 혼재한 상태가 저장되지 않고, 무한 사이클 도중 레벨업하면 엉뚱한 슬롯이 갱신됐습니다.
원인
세 버그의 원인이 같았습니다. 현재 위치를 "시퀀스 안에서의 위치"로 관리하고 있어서, 시퀀스가 교체되는 순간 그 위치가 의미를 잃었던 것입니다.
해결
위치를 전체 데이터 시트의 절대 행 인덱스로 바꿨습니다. 시퀀스가 교체돼도 인덱스는 그대로 유효하고, 이중으로 들고 있던 상태가 사라지면서 버그 3건이 동시에 해결됐습니다.
배운 것 — 비슷한 버그가 여럿이면 개별 수정보다 상태 모델 자체를 의심해야 합니다.
Troubleshooting 04

실패를 감지하지 못하던 폴백 로직

문제
보상 테이블은 서버에서 받고 실패 시 로컬 파일로 폴백하는 구조였습니다. 그런데 역직렬화 라이브러리가 구조가 맞지 않는 데이터도 예외 없이 받아들여, 모든 필드를 기본값으로 채운 빈 행을 만들어냈습니다. 파싱이 "성공"한 것으로 보여 폴백이 발동하지 않았습니다.
위험도
결제가 걸린 콘텐츠라 데이터 오류가 곧바로 문의로 이어질 수 있었습니다.
해결
존재 여부 검사만으로는 부족하다고 판단해 내용 기반 유효성 검사를 추가했습니다. 레벨 범위와 보상 항목이 실제로 채워진 행이 하나라도 있어야 정상 데이터로 인정하도록 하고, 같은 시트를 읽는 다른 곳에서도 동일 기준을 쓰도록 판정을 공유했습니다.
배운 것 — 파싱 성공이 데이터 정상을 뜻하지 않습니다. 폴백은 실패를 감지할 수 있어야 의미가 있습니다.

온보딩 문서 작성

기능을 완성한 뒤, 이 이벤트를 처음 만지는 사람이 한 번 읽고 작업을 시작할 수 있도록 사내 시스템 가이드 문서를 직접 작성했습니다. 시스템 개요 · 진입 흐름 · 클래스 다이어그램 · 책임 분리표 · 데이터 시트 명세 · 로드 흐름으로 구성했습니다.

블로그에 다이어그램을 그려 개념을 정리하던 습관이, 실무 문서로 이어진 결과물입니다.

Case · 유저 자산 소실 방지

프리셋에 등록된 칩이 자동합성으로 사라지는 문제

문제
칩을 재련하면 효과 ID가 바뀝니다. 그런데 그 칩이 프리셋에 등록돼 있으면 ID가 바뀌는 순간 프리셋 보호가 풀려, 이후 자동합성 과정에 휩쓸려 사라질 수 있었습니다. 유저 입장에서는 아껴둔 칩이 이유 없이 없어지는 상황입니다.
추적이 어려웠던 이유
재련 → ID 변경 → 보호 해제 → 자동합성 소실로 이어지는 3단계 연쇄였습니다. 재련 시점에는 아무 문제가 없어 보이고, 소실은 나중에 다른 기능에서 발생합니다.
해결
칩이 비활성 프리셋에 등록돼 있는지 검사하는 로직을 추가하고, 해당 칩은 재련 자체를 차단했습니다. 그냥 막기만 하면 유저가 이유를 알 수 없으므로 안내 토스트를 함께 띄우고 5개 언어로 로컬라이즈했습니다.
배운 것 — 기능 하나를 고칠 때 그 뒤에 무엇이 연결돼 있는지 따져봐야 한다는 걸 배웠습니다. 그리고 막는 것으로 끝내지 않고 왜 안 되는지 알려주는 것까지가 수정이라는 것도요.

그 외 대응한 문제

  • 기간제 칩 만료 처리 — 만료 시 타이머가 사라지지 않던 문제, 장착 상태에서 만료될 때의 안내 누락
  • 레드닷 오표시 — 받을 보상이 없는데 알림이 켜지거나, 있는데 안 켜지던 문제
  • 화면 전환 상태 꼬임 — 콘텐츠 종료 후 돌아왔을 때 하단 탭이 엉뚱한 곳을 가리키던 문제
  • 기기별 해상도 대응 — 특정 비율에서 UI가 잘리거나 겹치던 문제

신규 개발과 달리 라이브 수정은 이미 그 상태로 플레이 중인 유저가 있다는 전제에서 시작합니다. 고치는 것보다 고쳐도 안전한지 판단하는 데 시간을 더 썼습니다.

AI를 활용한 개발 방식

문서 731건 · 스킬 17종

3.5개월 안에 라이브 콘텐츠를 만들어내려면 코드베이스를 파악하는 시간과 테스트할 시간이 늘 부족했습니다. AI에게 코드를 대신 짜게 하는 대신, AI가 우리 팀의 규칙 위에서 일하도록 환경을 만드는 쪽을 택했습니다.

문제

수만 커밋 규모의 코드베이스에서 AI에게 그냥 작업을 시키면, 기존 설계 규칙을 모른 채 이미 있는 기능을 새로 만들거나 팀 컨벤션을 어기는 코드를 냈습니다. 매번 사람이 배경을 설명해주는 것도 그 자체로 비용이었습니다.

해결

게임의 시스템 구조를 Obsidian에 문서로 정리하고, 작업 키워드에 따라 관련 문서만 골라 읽는 스킬 17종을 만들었습니다.

코드 작성기존 규칙 위에서 시작
  • 필요한 문서만 로드 — 기본 문서 3~5개를 읽고, 작업 성격에 따라 세부 문서를 추가로 가져오도록 설계해 컨텍스트 낭비를 줄임
  • 세션당 1회 로드 — 같은 문서를 반복해서 읽지 않도록 제어
  • 컨벤션을 규칙으로 고정 — 서비스 접근 방식 등 팀 규칙을 별도 스킬로 분리해 항상 적용
  • 문서 생성도 자동화 — 구조 문서·온보딩 문서를 만드는 커맨드를 함께 구축해, 새 시스템을 만들면 문서가 따라오도록 순환 구조를 만듦
Result

작업을 시작할 때마다 코드베이스를 헤매던 시간이 사라졌고, 이미 있는 기능을 다시 만드는 일과 컨벤션 위반이 크게 줄었습니다. 무엇보다 이 문서들은 AI만이 아니라 팀원이 읽는 온보딩 자료로도 쓰였습니다.

② QA 전달용 테스트 체크리스트 작성

QA 협업

문제

팀에 QA 담당자가 있어 구현이 끝나면 검증을 요청하는 구조였습니다. 그런데 "이 기능 테스트 부탁드립니다" 정도로 넘기면, QA는 겉으로 드러나는 동작 위주로 확인하게 됩니다. 구현한 사람만 아는 경계 조건—어느 시점에 서버 값이 갱신되는지, 어떤 상태에서 나가면 위험한지—은 요청자가 짚어주지 않으면 검증 범위에서 빠집니다. 개발 일정이 촉박할수록 그 설명을 정리할 시간부터 없어졌습니다.

해결

기능을 완성한 직후 구현 내용과 변경 지점을 정리해 테스트 체크리스트를 생성하고, 실제로 발생 가능한 항목만 골라 QA 담당자에게 검증 요청과 함께 전달했습니다. 혼자서는 잘 떠올리지 못하는 동시성 · 경계 시점 · 비정상 종료 케이스를 빠짐없이 채우는 데 특히 효과가 있었습니다.

  • 플레이 중 UTC 리셋 시점이 지나가면 어떻게 되는가 → 로비 종료 및 상태 초기화
  • 강화 효과 지속시간이 전투 중 만료되면 → 진입 시점 기준으로 고정
  • 보상 연출 중 UI를 닫으면 보상과 화면 갱신이 어긋나는 문제
  • 서버 값이 예상 범위를 벗어날 때의 방어 코드
Result

QA 담당자가 무엇을 어떤 조건에서 확인해야 하는지를 요청 시점에 함께 받게 되면서, 되묻는 과정이 줄고 검증 범위가 넓어졌습니다. 위 항목들은 모두 라이브에 나가기 전에 방어 코드로 처리됐습니다. AI가 테스트를 대신한 것이 아니라 제가 놓친 질문을 던져준 것에 가깝고, 선별과 최종 판단은 직접 했습니다.

AI는 코드를 대신 써주는 도구가 아니라, 맥락을 주면 그만큼 정확해지는 도구라고 생각합니다. 그래서 코드를 시키기 전에 읽을 것을 먼저 만드는 데 시간을 썼습니다.
